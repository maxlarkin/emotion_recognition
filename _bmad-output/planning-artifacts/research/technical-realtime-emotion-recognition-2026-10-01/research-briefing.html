Technical research: real-time emotion recognition (video + audio) MVP

Decision this research serves: which open models (face + voice) to use for the MVP without fine-tuning, how to build the real-time pipeline on a laptop with 4 GB VRAM / 16 GB RAM, how to scale later to 20+ cameras, and what media quality requirements to draft.

Резюме для решения

Что делать. Собрать MVP на открытых моделях без дообучения: - лицо: YuNet (OpenCV) + EmotiEffLib enet_b0_8_va_mtl (ONNX), 7–8 классов, Apache-2.0 [1][9]; - голос: Silero VAD + GigaAM-Emo (Сбер, MIT, обучена на русском Dusha) [21][24]; - объединение: взвешенное позднее объединение вероятностей (late fusion) со сглаживанием во времени; - транспорт: WebSocket React ↔ FastAPI: кадры JPEG 5–10 fps и PCM 16 кГц; - инференс: в отдельном процессе, обрабатывается только последний кадр [28][33].

Одна веб-камера на ноутбуке с 4 ГБ VRAM / 16 ГБ RAM обслуживается с запасом. GPU-сервер для MVP не нужен.

Три ключевых вывода: 1. Лучшая открытая FER-модель даёт ~65–67% на AffectNet-7 и ~92% на RAF-DB [1][7][53]. Лучшая модель для живой русской речи даёт macro-F1 0.67 на 4 классах [21]. Два человека-разметчика AffectNet совпадают лишь в 60.7% случаев [46]. 2. Цели ТЗ 95% / 98% на реальных данных недостижимы. Такие цифры появляются только на сыгранных данных и при завышающих протоколах [52]. В регламент нужно вписать условия измерения: метрику, число классов, тип данных, разбиение по субъектам. 3. 20+ камер на одном 4-ГБ ноутбуке не помещаются: реально ~10–15 потоков видео или ~8–12 с аудио. Это оценка; прямых замеров нет [35][36][37]. - Обоснованный путь к 20+: горизонтальные узлы ноутбук-класса за шиной сообщений или один сервер класса T4/A2. На T4/A2 эталонный конвейер NVIDIA держит 31 поток 1080p30 [37]. - Аренда облачного T4 24/7 стоит ~14–15 тыс. ₽/мес и в бюджет 3 000 ₽ не укладывается [40][41].

Главная оговорка: все цифры скорости на целевом железе — экстраполяция. Первая задача разработки — замер на ноутбуке. Аудиоканал знает только 4 класса (angry / sad / neutral / positive); страх, отвращение и удивление даёт только видео.

1. Распознавание эмоций по лицу (FER)

Вопрос: какую открытую модель и какой детектор лиц взять для MVP без дообучения на ноутбуке с 4 ГБ VRAM.

Лидер — EmotiEffLib (бывший HSEmotion, А. Савченко, НИУ ВШЭ / sb-ai-lab). - Лицензия Apache-2.0, установка pip install emotiefflib (v1.1.1 от 2025-09-10). Бэкенды PyTorch и ONNX, API на Python и C++ [1][3]. - Точность по README на AffectNet-7 / AffectNet-8: - enet_b0_8_va_mtl: 64.94% / 61.93%; - enet_b2_8_best: 66.51% / 63.125%; - mobilenet_7: 64.71% (7 классов) [1]. - Размер модели: 14–30 МБ. Единственные опубликованные замеры скорости — на CPU телефона (Snapdragon 888): 16 / 59 / 191 мс для mobilenet / B0 / B2 [2]. Замеров на ноутбуке нет; их нужно сделать локально (confidence low для любой экстраполяции). - Репозиторий поддерживается: последний коммит 2026-06. Новых весов FER с 2025-09 нет [1]. - Команда HSEmotion заняла 1-е место в Expression Recognition на ABAW-8 (CVPR 2025, препринт) [4]. В ABAW-11 (2026-07, препринт) она использует те же замороженные лёгкие экстракторы MT-EmotiEffNet-B0 и MT-EmotiDDAMFN плюс временное сглаживание Гауссом [5]. Подход «модель по кадрам + временное сглаживание» соответствует текущей практике лидеров. - RAF-DB для EmotiEffLib в README не указан. Это пробел, но не блокер.

Альтернативы:

Модель AffectNet-7 AffectNet-8 RAF-DB Скорость Лицензия Вывод
EmotiEffLib B0 / B2 64.9 / 66.5 61.9 / 63.1 — 59 / 191 мс (CPU телефона) [2] Apache-2.0 берём
DDAMFN (MDPI 2023) 67.03 64.25 91.35 нет данных не проверена запасной вариант по точности; цифры из сниппета, confidence medium [7]
OpenFace 3.0 (FG 2025) — 59–60 — 38 мс/кадр, весь конвейер на десктопном CPU [6] только для исследований ниже точность
EMO-AffectNetModel (СПИИРАН) 66.4 (val) — — нет данных веса только для научного использования на русском RAMAS UAR лишь 44.3% [8]
LibreFace (WACV 2024) нет цифр нет цифр нет цифр «в 2 раза быстрее OpenFace 2.0» [58] USC research license нет метрик FER [12]
ViT (trpakov, FER2013) — — — 85.8M параметров Apache-2.0 тяжёлая; обучена только на FER2013 (71.16%) [13]

Детектор лиц: - YuNet — встроен в OpenCV (FaceDetectorYN), лицензия MIT. AP 0.88 / 0.87 / 0.75 на WIDER Face (easy / medium / hard). Ловит лица от ~10×10 px [57]. Скорость 0.69 мс на i7-12700K при входе 160×120 [9]. Для OpenCV 5.x нужна новая модель face_detection_yunet_2026may.onnx [57] (класс version, ≤1 мес — перепроверить при установке). - MediaPipe BlazeFace short-range (настроен под веб-камеру): 2.94 мс на CPU Pixel 6 [10]. - SCRFD-500M / 2.5G (InsightFace): точнее на сложных лицах (WIDER-hard 68.5 / 77.9). Скорость 3.6 / 4.2 мс при VGA, железо не подтверждено [11].

Трекинг вместо детекции на каждом кадре: детекция раз в N кадров плюс простой IoU/SORT-трекер. Единственный найденный замер — детекция на каждом 3-м кадре даёт ускорение в 2.25 раза ценой 4.7 п.п. покрытия, причём в задаче анонимизации [14] (confidence low). Для одной веб-камеры трекинг не нужен; он полезен при 20+ потоках.

Русские лица: открытой FER-модели, обученной на русских или славянских лицах, не найдено. Единственный ориентир — EMO-AffectNet на русском корпусе RAMAS: UAR 44.3% [8]. Это указывает на доменный разрыв и подтверждает требование ТЗ о дообучении.

Остановка: направление покрыто за 2 раунда (coverage). Открытые вопросы: латентность на 4-ГБ GPU и RAF-DB для EmotiEffLib.

2. Распознавание эмоций по русской речи (SER) и объединение модальностей

Вопрос: какую открытую SER-модель для русского языка взять без дообучения и как объединить её с моделью лица.

Главный вывод: открытой модели, которая одновременно (а) знает все 7 базовых эмоций и (б) проверена на естественной русской речи, не найдено. Есть выбор между широким набором классов и работой на живой речи.

Лидер — GigaAM-Emo (SaluteDevices / Сбер). - Энкодер GigaAM v1 (Conformer), дообученный на Dusha; число параметров в первоисточнике не указано (unverified). Лицензия MIT. Загрузка: gigaam.load_model("emo"), затем get_probs(path) [21]. - Метрики на Dusha из первоисточника evaluation.md [21]: - Crowd (сыгранная краудсорсинговая речь): UA 0.90 / WA 0.87 / macro-F1 0.84; - Podcast (спонтанная речь): UA 0.90 / WA 0.76 / macro-F1 0.67. - Для сравнения, baseline Dusha на Podcast даёт macro-F1 0.54 [20][21]. - Это единственный найденный результат на спонтанной русской речи для готовой модели. Метрики — самоотчёт авторов (confidence medium). Независимую проверку обещает oruk-bench, но результатов пока нет [26]. - Набор классов — от Dusha: angry / sad / neutral / positive (4 класса) [19]. Точный список меток модели в первоисточнике не найден; проверить вызовом get_probs (unverified). - Скорость: полный энкодер на CUDA обрабатывает 10 с аудио за ~10 мс при batch 1. GPU в источнике не указан [21]. По README модель экспортируется в ONNX, для GPU есть fp16 [21] (README прочитан при проверке).

Альтернативы:

Модель Классы Сыгранная речь Спонтанная речь Размер Лицензия
GigaAM-Emo 4 (Dusha) Crowd F1 0.84 Podcast F1 0.67 ~240M (unverified) MIT [21]
Aniemore wavlm-emotion-russian-resd 7, но вместо surprise — enthusiasm RESD F1 0.80 Podcast F1 0.11 [15] 317M MIT
Aniemore wav2vec2-xlsr-53-russian те же 7 RESD F1 0.72 Podcast F1 0.095 [16] 316M MIT
emotion2vec+ base / large 9 (все 7 базовых + other / unknown) на русском zero-shot не проверялся; base + линейная голова на RESD — WA 64.8% [17] нет данных 90M / 300M [18] MIT (репозиторий)
xbgoose hubert-large Dusha 5 (+other) F1 0.81, сплит не указан [23] нет данных ~316M не подтверждена
whisper-base-ser-dusha 5 (+other) Crowd F1 0.843 [22] нет данных 20.7M лицензия не указана [22]
  • Карточка Aniemore прямо предупреждает: модель обучена на сыгранной сбалансированной речи и на реальной речи завышает долю эмоций. В реальном материале ~93% фраз нейтральны [15].
  • Разрыв «сыгранная → живая речь» подтверждён и внутри Dusha. Baseline на Crowd — WA 0.76, на Podcast — WA 0.53. Около 90% подкастов нейтральны [20].
  • Бенчмарк EmoBox (INTERSPEECH 2024) включает RESD, но не включает Dusha. Числа по RESD опубликованы только картинками, извлечь их не удалось [25].

Датасеты для будущего дообучения: - Dusha: ~350 ч, ~300 тыс. клипов, 8 308 дикторов, 4 эмоции + other. Сырое аудио подкастов не раздаётся, доступны признаки [19][20]. - RESD: сыгранная речь, 7 эмоций, ~1 400 фраз, ~2.3 ч [25]. - RAMAS: мультимодальный (видео лица + речь), ~7 ч, 10 актёров, 6 базовых эмоций [27].

Объединение аудио и видео (fusion) для MVP: - VAD. Silero VAD тратит <1 мс на чанк 30 мс на одном потоке CPU, лицензия MIT [24]. Без речи аудиоканал отключается. - Окно. Подкасты в Dusha нарезаны по VAD на сегменты ~5 с [20]. Окна 2–5 с попадают в распределение обучения. - Метод. Взвешенное позднее объединение вероятностей (late fusion) на общем наборе меток. Лидеры ABAW объединяют признаки обученной MLP [4], а для MVP без обучения остаётся только late fusion. Эта схема в источниках этого прогона не подтверждена (confidence low); вес аудио подбирается эмпирически. - Отображение меток. Классы аудио (positive) сводятся к видеоклассам: positive → happiness. Fear, disgust и surprise даёт только видео.

Остановка: 2 раунда, coverage. Открытые вопросы: точный список меток GigaAM-Emo, латентность на конкретном 4-ГБ GPU, zero-shot emotion2vec+ на русском.

3. Архитектура real-time конвейера и масштабирование до 20+ камер

Вопрос: как собрать MVP на FastAPI + React на ноутбуке (4 ГБ VRAM, 16 ГБ RAM, веб-камера) и как обоснованно масштабироваться до ≥20 камер.

3.1 Транспорт браузер ↔ бэкенд (MVP)

Вариант Состояние Вывод
WebSocket: JPEG-кадры 5–10 fps + PCM16 16 кГц чанками 0.5–1 с стандартный FastAPI, без зависимостей рекомендуется для MVP
WebRTC через aiortc поддерживается, v1.15.0 от 2026-07-13 [28] риск: если recv() блокируется обработкой, задержка растёт до ~30 с. Нужен отдельный воркер и «только последний кадр» [28] (confidence medium)
WebRTC через fastrtc (Gradio/HF) pre-1.0: последний релиз 0.0.34 (2025-11), последний коммит 2026-01 [29] похоже на заброшенный проект, не брать
  • 30 fps для анализа не нужны. Frigate по умолчанию детектирует на 5 fps с потока 720p [33]. Браузер показывает локальный <video> и рисует поверх результаты; поэтому главное преимущество WebRTC здесь почти не нужно.
  • Паттерн бэкенда. WebSocket-обработчик кладёт кадр в слот размера 1 (старые кадры отбрасываются). Кадр забирает отдельный процесс инференса (multiprocessing): детектор + FER на ONNX Runtime. SER работает во втором воркере по аудиоокнам. Результаты уходят JSON-ом в тот же сокет. Это прямой вывод из проблем aiortc [28]; сама схема — синтез исследования (confidence medium).
  • Версии: onnxruntime-gpu 1.30.0 (2026-09-10, Python ≥3.11) [30]. GigaAM рекомендует onnxruntime-gpu==1.22.* [21]. Совместимость версий проверить при установке.

3.2 Бюджет ресурсов на ноутбуке

  • Лицо. YuNet — 0.69 мс, MobileFaceNet FER — 1.79 мс (112×112) на i7-12700K CPU [9]. EfficientNet-B0 из EmotiEffLib тяжелее, но для одного потока легко укладывается даже в CPU (оценка).
  • Детектор на GPU (ориентир). Frigate: YOLOv9-tiny-320 — 8 мс на RTX 3050 (ONNX) [32].
  • Речь. wav2vec2-base (95M) на 8-ядерном CPU работает с RTF 0.083 [39] (confidence medium-low, один любительский бенчмарк). Энкодер GigaAM на CUDA: ~10 мс на 10 с аудио [21].
  • Память. fp16 занимает ~2 байта на параметр [34]: модель на ~240M параметров — около 0.5 ГБ VRAM. Вместе с моделью лица это укладывается в 4 ГБ (оценка, unverified).
  • Вывод для MVP. 1 веб-камера + микрофон в real-time на ноутбуке выполнимы с запасом. Латентность на конкретном GPU нужно замерить (nvidia-smi dmon).

3.3 Сколько потоков вытянет ноутбук с 4 ГБ GPU

Прямых бенчмарков на GTX 1650 / RTX 3050 4 ГБ не найдено. Оценка ниже собрана из официальных таблиц NVIDIA и ускорений, перенесённых с RTX 2080S [35][36][37][38].

Конфигурация Потоков (оценка) Узкое место
GTX 1650, только видео, 1080p30 на входе, анализ 5 fps ~10–15 NVDEC и GPU-инференс
GTX 1650, подпотоки 720p / 15 fps ~12–16 GPU-инференс
RTX 3050 laptop, только видео, 720p ~16–20 (на грани) GPU и VRAM
Любой из них + SER на каждый поток ~8–12 SER: CPU или GPU
  • Декодирование. NVDEC Turing даёт ~771 fps H.264 1080p [35]. Сессии на GeForce не ограничены, но буферы декодера занимают VRAM [35]. Модератор NVIDIA пишет, что GTX 1650 — «менее половины возможностей декодирования T4» [36]. Два источника NVIDIA дают 15–25 потоков 1080p30; рабочая оценка — ~15 (нижняя граница).
  • Опорная точка сервера. Эталонный конвейер DeepStream (детектор ResNet18 960×544 INT8 + трекер + 2 классификатора, batch 32) держит 31 поток H.264 1080p30 на T4 и A2; L4 — 68; Jetson Orin Nano — 8 [37]. Проверено по первоисточнику.

3.4 Масштабирование до ≥20 камер — варианты

Вариант Когда Обоснование
A. Один узел. MediaMTX перед камерами (v1.21.1, 2026-09-20) [31] → аппаратное декодирование подпотоков 720p → выборка 5 fps [33] → лица со всех потоков батчем в один ONNX/TensorRT-воркер ~20 камер на сервере класса T4/A2/L4; на 4-ГБ ноутбуке — до ~10–15 [31][33][35][37]
B. Горизонтально. N узлов-воркеров (по ~10–12 потоков на ноутбук-класс), шина Redis Streams / NATS, результаты в UI через WebSocket/SSE, события в PostgreSQL без серверного GPU: 2 ноутбук-класса узла на 20 потоков с SER паттерн; практических разборов в прогоне не найдено (confidence low)
C. DeepStream / Triton максимум пропускной способности тяжёлый стек, только NVIDIA; для MVP избыточен [37]
D. Аренда облачного GPU если своего сервера не будет T4 у immers.cloud — $0.23/ч [40]; Selectel ~19 ₽/ч, Yandex Cloud ~79 ₽/ч (агрегатор, confidence medium) [41]. 24/7 это ~14–15 тыс. ₽/мес, выше бюджета 3 000 ₽

Вывод под ограничения пользователя: без GPU-сервера 20+ потоков с аудио на одном 4-ГБ ноутбуке не помещаются. Обоснованный путь масштабирования — горизонтальный (вариант B): несколько узлов ноутбук-класса или один сервер класса T4/A2 (вариант A). Код MVP стоит сразу писать с разделением «приём потока → очередь → воркер инференса», тогда переход между вариантами не потребует переписывания.

Остановка: 2 раунда, coverage. Открытые вопросы: замеры на целевом GPU, CPU-стоимость программного декодирования, официальные цены облаков.

4. Требования к медиаконтенту и реалистичность целей точности

Вопрос: какие параметры видео и аудио минимально нужны для надёжного распознавания и достижимы ли 95% (поток) и 98% (запись).

4.1 Реалистичность 95% / 98%

На реальных («in-the-wild») данных с 7+ классами цели 95–98% в литературе не достигаются.

Данные Лучший найденный результат Источник
RAF-DB (фото, 7 классов) ~92% (POSTER++ 92.21%) [53] (confidence medium, сниппет)
AffectNet-7 ~67% (DDAMFN 67.03%, EmotiEffLib 66.5%) [7][1]
DFEW (видео) WAR 76.6% / UAR 65.3% [54] (препринт, сниппет)
MAFW (видео, 11 классов) WAR 58.7% [54]
Dusha Podcast (живая русская речь, 4 класса) macro-F1 0.67 [21]
RAVDESS (сыгранное аудио+видео) 96.11% — на случайном разбиении 80/20, не независимом от актёров [52]
  • Потолок задаёт разметка. Два разметчика AffectNet совпадают лишь на 60.7% изображений [46]. «Точность» выше согласия людей на таких данных бессмысленна.
  • 95%+ встречаются только на сыгранных или лабораторных данных и при протоколах, завышающих результат [52]. CK+ / JAFFE / RESD в оригинальных статьях в этом прогоне не проверены.
  • Условия, при которых 95% правдоподобны (гипотеза, опирается на [20][46][52]):
  • позированные выражения лица;
  • фронтальные лица ≥100 px;
  • 3–4 класса или бинарная задача (негатив / не негатив);
  • агрегация по клипу или сессии, а не по кадру;
  • тест на том же домене.
  • Рекомендация для регламента: фиксировать метрику (UAR / macro-F1, а не только accuracy), число классов, тип данных и разбиение, независимое от субъектов.

Открытого русского FER-датасета на видео, кроме RAMAS, не найдено. Для дообучения на «российском медиаконтенте» скорее всего придётся размечать собственный корпус.

Остановка: 2 раунда, раунды исчерпаны. Открытые вопросы: fps, освещение, реверберация, минимальная длина сегмента, первоисточники CK+ / JAFFE / RESD, текст ГОСТ / IEC 62676-4.

Выводы на стыке направлений

  • Классы аудио и видео не совпадают, и это определяет схему объединения. Лучшая русская SER-модель знает 4 класса [21]. Лучшая FER-модель знает 7–8 [1]. Аудио может подтверждать или опровергать только «гнев / грусть / позитив / нейтраль». Fear / disgust / surprise распознаются только по лицу. Отсюда late fusion по общим классам, а не единая мультимодальная модель.
  • Нейтральная доминанта. В живой речи ~90% фраз нейтральны [20]. В уличном видео большинство кадров, скорее всего, тоже нейтральны (unverified). Модель, обученная на сыгранных данных, на живом потоке завышает эмоции [15]. Поэтому в интерфейсе нужны пороги уверенности и временное сглаживание; сглаживание применяют и лидеры ABAW [5].
  • Требования к медиа и пропускная способность конфликтуют. Для лица ≥100 px нужна высокая плотность пикселей (~500 px/м) [42][44]. Значит, нужен основной поток высокого разрешения, а он упирается в декодирование на 4-ГБ GPU [35][36]. Компромисс — подпоток 720p при камерах, расставленных так, чтобы лица были крупными. Это инженерный вывод, не измерение.
  • Требование ТЗ «дообучение на российском контенте» упирается в данные. Русская речь покрыта (Dusha, RESD) [19][25]. Для русских лиц на видео есть только сыгранный RAMAS [27], а модель EMO-AffectNet на нём даёт UAR 44.3% [8]. Для видео основной объём работы по дообучению — сбор и разметка своего корпуса.
